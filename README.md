# Forge

A system-independent **Change Integrity Engine**. Forge turns changes in
evolving systems (filesystem, Git, Docker, and eventually more) into
structured, observable, planned, executable, verifiable, and
compensatable operations:

```
STATE -> OBSERVE -> CHANGE -> PLAN -> REVALIDATE -> EXECUTE -> VERIFY -> COMMIT
                                              (failure path)
                                    EXECUTE -> FAIL -> COMPENSATE -> VERIFY -> COMPENSATED
```

Forge is not Terraform, not Git, not Kubernetes, not CI/CD, not an AI
agent. It's the missing protocol layer underneath tools like those.

**Start here:**
- [`RFC/0001-protocol-overview.md`](RFC/0001-protocol-overview.md) —
  the protocol itself, independent of this Rust implementation.
- [`docs/adr/`](docs/adr/) — every non-obvious architectural decision,
  with reasoning and consequences.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — the invariants a change must
  respect, and the process for proposing to change one.

## Status: v0.1 scaffold (Phase 0 + partial Phases 1-3, 11-13)

This repository was generated by an AI pair-programming session and
**has not yet been compiled** in the environment that generated it (no
Rust toolchain / no network access to crates.io were available there).
Treat it as a strong, internally-consistent starting point — architecture,
types, schemas, migration, and a working filesystem plugin/CLI skeleton —
not as a tested release. See "Build & verify" below for the first thing to
run.

### What's real and implemented

- **Phase 0** — 6 ADRs (`docs/adr/0001`-`0006`) covering every non-obvious
  architectural decision, 7 JSON schemas (`schemas/`) for every protocol
  primitive, and 5 acceptance-test scenarios (`integration-tests/tests/`)
  mirroring Sections 26-30 of the original spec.
- **Phase 1** — Rust workspace with 14 crates, strict dependency direction
  (Core never depends on CLI — ADR 0001), shared id/error/timestamp types.
- **Phase 2** — Resource, Observation, Relation (`forge-resource`),
  the four State perspectives (`forge-state`), a dependency graph for
  blast-radius queries (`forge-graph`, not yet wired into the CLI — see
  below).
- **Phase 3** — SQLite schema + migration (`crates/forge-storage/migrations`)
  implementing the mutable-current-state + append-only-history split from
  ADR 0002, plus reader/writer methods for every table (resources,
  changes, actions, plans, executions, action_results, evidence) and a
  test that greps the storage crate for accidental `UPDATE`s on
  append-only tables (with two narrow, documented exceptions —
  `executions.state` and `plans.status` — see the doc comments on
  `update_execution_state` and `mark_plan_stale`).
- **Change / Plan / Risk / Execution / Verification / Compensation /
  Policy / Evidence** domain types (Sections 9-21) each in their own
  crate, each with unit tests exercising the specific invariant it's
  responsible for (stale-plan blocking, approved-plan immutability,
  deterministic risk scoring, compensation-is-not-rollback, default-deny
  policy, etc).
- **Phase 5/7/8/9 (filesystem-only slice)** — `forge plan` and
  `forge apply` are wired end-to-end for the filesystem plugin: `plan`
  diffs a fresh scan against the last stored snapshot, builds
  Change+Action pairs, assesses risk (ADR 0006), and persists an
  APPROVED plan (refusing to auto-approve without `--yes`, per Section 23
  default-deny / Section 30 irreversible-critical). `apply` revalidates
  against fresh observations (Section 14 — blocks and marks the plan
  STALE if reality drifted), executes, verifies each target
  (Section 16), and commits or walks the compensation path
  (Section 17), recording evidence rows the whole way.
- **Phase 11** — a real `forge` CLI binary: `init`, `scan`, `plan`,
  `apply` work end-to-end against SQLite; `state`, `changes`, `inspect`,
  `history`, `evidence` all read real data. `diff`, `verify` (as a
  standalone command), and `compensate` (as a standalone command) are
  honest stubs — `verify` and `compensate` as *concepts* are already
  exercised automatically inside `apply`, just not independently
  callable yet.
- **Phase 12** — a working filesystem plugin that scans a directory tree
  into Resources and can observe/write files.
- **Phase 13** — a working Git plugin (`plugins/git`) that shells out to
  the system `git` binary: it represents the repository and each tracked
  file as Resources, links them with `Contains` Relations (real input for
  `forge-graph`), and implements `git.commit` (compensation: supported,
  via revert/reset) and `git.checkout` (compensation: partial, since
  uncommitted working-tree changes between checkouts are not
  recoverable). Not yet wired into `forge plan`/`forge apply` — see
  "What's stubbed" below.

### What's stubbed or not started

- **Phase 4** — there is no dedicated "detect changes as a first-class,
  reviewable step separate from planning" command yet; `forge plan`
  currently does detection and planning in one step for the filesystem
  plugin. Splitting these, and adding a `forge diff` that shows DESIRED
  vs OBSERVED (Section 7) rather than just OBSERVED-then-OBSERVED-again
  drift, is the next real gap.
- **`forge plan`/`forge apply` are filesystem-only** — the Git plugin
  (Phase 13, above) is implemented and unit-tested on its own, but the
  CLI's plan/apply pipeline is not yet generalized to run against more
  than one plugin at a time. `forge-graph`'s `dependency_count` in
  `forge plan`'s risk calculation is hardcoded to `0` as a direct
  consequence (see the `TODO` in `crates/forge-cli/src/commands/plan.rs`)
  — `forge-graph` itself is implemented and tested; it has real
  `Contains` relations available from the Git plugin now, they are just
  not yet consumed by the CLI.
- **Phase 14** — the Docker plugin (`plugins/docker`) is a stub with a
  documented planned shape; every method currently returns "not yet
  implemented". It is the highest-value plugin left to build, since it is
  the one the Section 26 MVP scenario (`api:v1.4 -> v1.5`) and Section 27
  failure scenario are written against, and it is the one with real,
  reliably supported compensation (restore the previous image tag).
- **Phase 15** — WASM plugin boundary (ADR 0005). `forge-plugin` defines
  the `Plugin` trait and `HostCapabilityGate` capability-check choke point
  today with an in-process implementation; swapping the backing
  implementation to `wasmtime` without changing callers is the whole
  point of the trait boundary, but that swap hasn't been done. Until it
  is, both in-process plugins (filesystem, Git) bypass capability
  enforcement — this is tracked explicitly as a known gap in ADR 0007,
  not silently accepted.
- **No interactive approval prompt** — `forge plan --yes` is a blunt
  stand-in for the interactive approval flow Section 30 implies. A real
  `forge approve <plan-id>` command (reviewing risk/compensation gaps
  before committing) is worth adding before this is anything more than a
  demo.

## Build & verify

This was written without a compiler available, so **the first thing to do
is build it**:

```bash
cd forge
cargo build --workspace
cargo test --workspace
```

Expect to fix minor issues — dependency version pins in `Cargo.toml` are
reasonable-as-of-early-2025 guesses (`rusqlite 0.31`, `clap 4`, `walkdir 2`,
etc.) and may need bumping; `rusqlite`'s `bundled` feature requires a C
compiler (`cc`) to be available for building SQLite from source.

Once it compiles:

```bash
cd /tmp/some-project
/path/to/forge/target/debug/forge init
/path/to/forge/target/debug/forge scan
/path/to/forge/target/debug/forge state
```

## Repository layout

```
crates/           Core domain crates (no clap, no AI, no network — ADR 0001)
plugins/          Plugin adapters (filesystem, git: real; docker: stub)
schemas/          JSON Schema for every protocol primitive
docs/adr/         Architecture Decision Records — READ THESE FIRST
RFC/              Protocol-level RFCs, starting with RFC 0001
integration-tests/ Acceptance scenarios A-E from the original spec
CONTRIBUTING.md   Invariants and process for proposing a change
```

## Continuing the work (suggested order)

1. `cargo build --workspace` and fix whatever the compiler finds — treat
   every fix as a chance to check it against the relevant ADR. This is
   still the most important next step; none of this has been compiled.
2. Split `forge plan`'s detect-vs-plan step (see "What's stubbed" above)
   and add a real `forge diff` (DESIRED vs OBSERVED, Section 7).
3. Generalize `forge plan`/`forge apply` to run against more than one
   plugin at once, and wire the Git plugin's `Contains` relations into
   `forge-graph` so `dependency_count` stops being hardcoded to 0.
4. Implement the Docker plugin (Phase 14) — this unblocks the exact MVP
   scenario in Section 26 (`api:v1.4 -> v1.5`) since it's the one with
   real, supported compensation (restore previous image tag).
5. Add `forge approve <plan-id>` as a real interactive step instead of
   the `--yes` flag stand-in, so risk/compensation gaps are reviewed
   before committing, not just before persisting.
6. Route both in-process plugins (filesystem, Git) through
   `HostCapabilityGate` (closing ADR 0007), independent of whether the
   Phase 15 WASM sandbox has landed yet — capability *checking* and
   capability *sandboxing* are separable pieces of work.
7. Only then: WASM sandboxing (Phase 15).

Do not skip ahead to Kubernetes/Terraform/Cloud/AI integrations — Section
31 of the original spec excludes these from v0.1 for a reason: the goal is
a small, hard-to-replace Core, not a large product (Section 38).
